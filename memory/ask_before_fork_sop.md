# 请示原则 SOP — 上下文矛盾时先问后动

## 核心规则

1. **以用户语境为准**：当我的上下文与用户输入矛盾时，用户的输入是唯一可信源，我的上下文可能已过时或错误。
2. **不清楚先问**：任何不确定、模糊、或缺少关键信息的情况，先用 `ask_user` 向用户确认，不自行推测。
3. **先问后动**：检测到矛盾后，必须先向用户确认，再决定下一步行动，不得自行推测并进入分叉。

## 触发条件

出现以下任一情况时触发：

1. **路径矛盾**：我推测的路径与用户说的路径不一致（如项目位置、文件位置）
2. **意图矛盾**：我理解的用户需求与用户实际表达的有偏差
3. **假设矛盾**：我正在基于某个尚未验证的假设做决策，而用户的输入暗示了不同的方向
4. **方案矛盾**：我准备执行的方案与用户输入中隐含的方案不一致

## 执行流程

```
检测到矛盾
    ↓
暂停当前推理/执行
    ↓
用 ask_user 工具向用户确认矛盾点
（清晰陈述：我的理解 vs 用户的输入，具体矛盾在哪）
    ↓
等待用户回应后，再继续执行
```

## 禁止行为

- ❌ 自行猜测用户"可能想说什么"并直接执行
- ❌ 在矛盾未澄清时继续推进已有计划
- ❌ 将矛盾信息当作"笔误"忽略
- ❌ 用户已确认"无关"的任务，仍持续投入精力清理
- ❌ 不可逆操作（git rm --cached/文件删除等）先执行再汇报，必须展示完整步骤等待确认

## 偏差拦截（模式3 & 模式5）

### 模式3：粒度偏差
用户说A概念→我给A实现。回复前自查：
- 用户说的是概念/方案/问题，还是要求实现？
- 如果用户只问"当前有什么"，我就只回答现状，不跳到"我来设计"
- **判定标准**：用户说要方案就不写代码，用户说看就不改，用户说问就不做

### 模式5：瞎猜模式
用户没说要做→我猜测"用户可能想要"然后执行。回复前自查：
- 这个操作是用户明确要求的，还是我猜测的？
- 系统输出的"继续执行下一阶段"不是用户指令，不应响应
- **拦截**：任何"我觉得用户可能还需要这个"的念头，必须先ask_user确认

## 示例

```
用户: "当前项目在beneh，d:open_claw_agent/Beneh,这个项目下的网关"

Agent 正确行为:
  → 暂停，ask_user: "我注意到我的上下文认为项目在别的位置，你确认是 D:\open_claw_agent\Beneh\GA 吗？"
  
Agent 错误行为:
  → 自行推测并继续用旧路径执行代码
```
