GenericAgent 智能体系统设计总览

基于 docs/ 下全部文档的综合整理 | 2026-05-09

概述

GenericAgent（GA）是一个通用型自进化LLM智能体系统，旨在实现本地计算环境内任务自动化。其核心设计理念是通过优化上下文信息密度来提升智能体性能，而非单纯扩展上下文长度。

核心定位

  • 模型无关：底层推理引擎（Claude、GPT、Gemini等）可替换，不影响执行逻辑、工具接口与内存架构
  • 统一智能体循环：每一步将全局记忆与当前任务规范结合形成执行上下文
  • 两种执行模式：交互模式（用户发起）与反射模式（环境触发）
  • 代码极简：核心代码库约3300行，核心智能体循环仅92行

核心设计原则

原则描述
工具最小化将工具限制在必要的最小集合内，避免上下文膨胀；满足原子性与组合泛化
分层记忆仅保留小型常驻可见层（L1），深层记忆（L2~L4）按需访问
自我进化通过记录与更新信息环境实现跨任务经验整合，不修改基础模型
上下文压缩设定<3万标记紧缩预算，采用字符域启发式方法管理

执行模式

交互模式

用户通过CLI或前端界面发起任务，智能体按步骤执行：用户输入 → put_task(query) → 构建prompt调用LLM → LLM返回响应(含工具调用) → 执行工具 → 更新上下文 → 循环直到完成。

sequenceDiagram participant U as 用户 participant CLI as 命令行 participant A as GenericAgent participant T as 工具引擎 participant L as 语言模型 U->>CLI: 输入任务指令 CLI->>A: put_task(query) A->>L: 构建prompt调用 L->>A: 返回响应(含工具调用) A->>T: 执行工具 T->>A: 返回结果 loop 循环直到完成 A->>L: 更新上下文/继续 L->>A: 返回响应 end A->>CLI: 最终结果 CLI->>U: 显示结果
flowchart TD A[开始] --> B[构建消息] B --> C[调用LLM] C --> D{解析工具调用} D -->|有工具调用| E[执行工具] D -->|无工具调用| F[直接响应] E --> G[更新上下文] G --> H{是否完成} H -->|否| B H -->|是| I[结束] F --> I

反射模式

无需用户指令，持续监控环境变化：加载监控脚本 → 定时轮询 check() → 条件满足时触发任务。

flowchart TD A["启动反射模式"] --> B["加载监控脚本"] B --> C["定时轮询 check()"] C --> D{条件满足?} D -->|是| E["触发任务"] D -->|否| C E --> F["执行任务"] F --> G["记录日志"] G --> C

典型应用：看门狗（监控文件/日志变化）、定时任务（按时间规则生成GA任务）

工具系统

定义与加载

工具定义在 assets/tools_schema.json，采用OpenAI Function Calling格式。启动时由agentmain.py读取：

TS = open('assets/tools_schema.json').read()
TOOLS_SCHEMA = json.loads(TS)

9个内置工具：

类别工具功能
文件操作file_read读取文件，支持关键词搜索
file_patch精准编辑，唯一匹配替换
file_write覆盖/追加/前置写入
代码执行code_run受控运行时执行Python/PowerShell
Web交互web_scan获取浏览器页面HTML/Tab列表
web_execute_js执行JS控制浏览器
内存管理update_working_checkpoint短期工作记忆
start_long_term_update长期记忆蒸馏
人机协作ask_user需要用户决策时中断任务

调用流程

用户输入 ↓ LLM 收到 tools=TOOLS_SCHEMA ↓ LLM 决定调用哪个工具 → 返回 function_call ↓ agent_runner_loop() 解析 → 映射到同名 Python 函数 ↓ 执行结果送回 LLM → 继续推理或输出回复

创建新工具

✅ 可以：脚本级工具

通过 file_write + code_run 运行时创建。例：图床服务、OCR调试脚本。

❌ 不可以：动态注册FC工具

tools=[] 列表在对话开始时固定，中途不能追加。需要编辑 assets/tools_schema.json + 写Python实现，下轮会话生效。

策略

  • 反复使用的能力 → 写成 .py 模块放 memory/ 下
  • 一次性任务 → 直接用 code_run 内联代码
  • 持久化服务（如图床） → file_write 创建 → code_run 启动后台进程

设计原则

  • 描述即行为约束：工具的description直接影响LLM使用决策
  • 参数驱动：所有交互通过参数传递
  • 一次一个工具：每轮LLM只输出一个工具调用或纯回复
  • 失败回溯：错误信息送回LLM，自主重试或换方案

分层记忆系统

L0~L4 层级

层级存储路径内容特点
L0 元规范memory/memory_management_sop.md记忆管理的元规则写记忆前必读
L1 索引层memory/global_mem_insight.txt紧凑指针、关键词映射、硬约束常驻内存核心，≤30行
L2 事实层memory/global_mem.txt经验证的长期事实严格准入，排除瞬态信息
L3 SOP层memory/*.md / *.py可复用流程性知识工作流、前置条件、故障处理
L4 归档层memory/L4_raw_sessions/历史会话原始数据自动收集，轨迹重构

访问与写入流程

graph LR L1[L1 索引层 常驻内存] -- 快速导航 --> L2[L2 事实层] L1 -- 快速导航 --> L3[L3 SOP层] L2 -- 经验整合 --> L3 M[智能体] -- 按需访问 --> L1 M -- 触发式提交 --> L2 M -- 触发式提交 --> L3 M -- 轨迹重构 --> L4[L4 归档层 历史会话]
收到任务 → 读L1 Insight → 发现SOP名 → 读L3 SOP → 按SOP执行 ↓ 任务完成 → 提取经验 → 按META-SOP决策树分类 ├─ 环境事实 → L2 global_mem.txt ├─ 通用规则 → L1 RULES └─ 特定技术 → L3 SOP/utils

规范须知：修改L1/L2只能用 file_patch 少量修改；写记忆前先读META-SOP(L0)核验；L2/L3变更时同步更新L1索引。

认知架构

环境感知

静态上下文（每次对话注入）：CONSTITUTION（9条铁律）、RULES、Global Memory Insight、Tool Definitions。

动态上下文（运行时注入）：cwd、Today、Working Memory（update_working_checkpoint）、会话历史。

探测手段：

  • file_read → 读文件内容
  • web_scan → 获知浏览器Tab + 页面HTML
  • code_run → 执行Python探测系统状态
  • 间接：工具返回值错误信息、用户反馈

资源定位

优先级方法适用场景
1查 Global Memory Insight已知内存中有什么
2读 SOP / import Utils有现成方案
3code_run 探测检查系统状态/文件存在性
4Metaso API 搜索查技术文档/API
5浏览器 Bing 搜索兜底

搜索铁律：搜文件名严禁不用es(禁PS递归/禁dir遍历) — 优先搜索索引，不暴力遍历。

问题解决循环

接收任务 → 查记忆/读SOP → 探测环境状态 → 执行一步操作 → 验证结果 ├─ 成功 → 继续下一步 └─ 失败 → 升级策略 ├─ 1次：读错误日志 ├─ 2次：探测环境 └─ 3次：换方案或问用户 → 闭环确认（保存记忆/Git）

核心原则：

原则说明
探测优先不空想结果，先用工具获取真实信息
分步执行限制失败半径，小步快跑
失败升级禁止无新信息的重复操作
交叉验证不信摘要，数值进详情页核实
闭环物理模拟后确认，Git完整闭环

自我反省机制

反省能力通过结构化的多层反馈回路和强制元认知机制实现，而非拟人化的意识活动。

五层反省体系

维度实现方式时间范围
即时反省<summary> 强制回顾上步结果+本轮意图每轮对话
任务中反省update_working_checkpoint 保存检查点任务中途
失败反省3次升级链：读日志→探环境→换方案失败时刻
长期反省记忆蒸馏 + META-SOP 写前校验跨会话
学习反省start_long_term_update 系统性回顾长任务完成时

失败升级链（3次法则）

第1次失败 读错误日志，理解原因 — 被动反省

第2次失败 探测环境状态，获取更多上下文 — 主动反省

第3次失败 深度分析后换方案或问用户 — 根本性调整

核心约束：禁止无新信息的重复尝试。每次重试必须基于新的信息或不同策略。

目标设定与验证机制

核心思想：每个粒度的行动都有明确的预期目标，执行后必须验证目标是否达成。

四层目标闭环

层级粒度机制
会话级跨任务start_long_term_update 蒸馏回顾
任务级完整任务plan.md 终止检查 + 独立Subagent验证
步骤级单一步骤[ ] 标记 + Mini验证（确认文件存在/exit code/页面状态）
单轮级每轮<summary> 意图声明 + 结果确认

独立验证机制

所有 plan mode 任务完成后，强制启动独立验证 subagent：

  • 创建 verify_context.json（任务描述、plan路径、交付物清单、必做检查）
  • 启动验证 subagent → 对抗性验证（"证明交付物不能用"）
  • 输出 VERDICT：PASS ✅ / FAIL ❌ / PARTIAL ⚠

多智能体系统

GenericAgent 支持四种多智能体协作模式，核心通讯基于文件系统异步IO协议 + 共享记忆。

主从模式（Master-Subagent）

主Agent通过文件系统与Subagent通讯：

文件方向用途
input.txt主→子任务目标与约束
context.json主→子绝对路径、交付物清单
output.txt子→主执行输出，[ROUND END]标记轮次
reply.txt主→子继续对话/追加指令
_intervene主→子纠偏指令
_keyinfo主→子注入working memory
_stop主→子终止信号

启动方式：

python agentmain.py --task my_task --input "任务描述" [--bg] [--llm_no N]

Map并行模式

适用独立同构子任务的批量处理：

  1. 主Agent准备N个独立输入文件
  2. 对每个文件启动一个 Subagent（--bg 后台）
  3. 等所有完成 → 读取各 output*.txt → 汇总结果

监察者模式（Supervisor-Worker）

监察者（Supervisor）— 只读、只判断、只干预，不下场干活 │ 读 output.txt（观察进度） │ 写 _intervene / _keyinfo（纠偏） ▼ 工作Agent（Worker） — 实际执行任务

监察者干预清单：跳步、细节遗漏、光说不做、断言无据、连续失败等。

共享记忆机制

所有Agent共享同一套记忆系统：L1 Insight、L2 Facts、L3 SOP/utils、keychain、文件系统。

多模型配置

通过 --llm_no N 参数为不同Subagent指定不同大模型：

# OCR 智能体 → 视觉模型 (llmclients[0])
python agentmain.py --task 截图分析 --input "..." --llm_no 0 --bg

# 文本智能体 → 纯文本模型 (llmclients[1])
python agentmain.py --task 文本摘要 --input "..." --llm_no 1 --bg

在 mykey.py 中定义多个 session config（变量名需含 api / config / cookie）。

自我进化

GA不修改基础模型，通过记录与更新信息环境实现进化。核心策略：进化策略而非工具，固定工具层与进化知识层分离。

技能树与自主探索

组件说明
技能树两级结构：类别（web自动化/数据处理）→ 具名技能，记录脚本与使用次数
触发机制任务模式（文件系统提交）或反射模式（定时轮询）

📌 体系特点：GA的核心价值在于，通过工具最小化 + 分层记忆 + 强制反省 + 文件系统IPC的组合，在极简架构（~3300行核心代码）上实现了自我进化、多智能体协作、反射式监控等高级能力。这些能力不是预先设计的特性，而是从底层架构中自然涌现的。
