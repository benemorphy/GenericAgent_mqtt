# Agent 演进中的目标设定与检查机制

> 基于 GenericAgent 系统的多层级目标-验证闭环架构
> 创建日期：2026-05-08

---

## 概述

本 Agent 的"演进"（任务执行与自我迭代）严格遵循 **目标先定 → 事后验证** 的闭环。这不是模糊的理念，而是嵌入在多个系统层的强制机制。核心思想是：**每个粒度的行动都有明确的预期目标，执行后必须验证目标是否达成，未达成则触发升级处置**。

目标-检查机制跨越 4 个粒度层级：

```
会话级 (Session)     ← start_long_term_update 蒸馏回顾
   ↑↓
任务级 (Task)        ← plan.md / checkpoint 终止检查
   ↑↓
步骤级 (Step)        ← [ ]标记 + Mini验证
   ↑↓
单轮级 (Turn)        ← <summary> 意图声明 + 结果确认
```

---

## 第一层：单轮级（Per-Turn）—— 最细粒度的目标循环

### 机制

每轮回复开头强制输出 `<summary>`，格式固定为：

```
<summary>上步结果新信息 | 本次意图（<30字）</summary>
```

### 目标设定与检查流程

```
[本轮开始]
    │
    ├── ① 声明意图 → <summary> 中写入 "本次意图"
    │
    ├── ② 执行工具调用
    │
    └── ③ 检查结果
         ├── 成功 → 下轮<summary>报告结果
         └── 失败 → 触发3次升级链
                      ├─ 1次：读错误日志
                      ├─ 2次：探测环境状态
                      └─ 3次：换方案或问用户
```

### 示例

```
<summary>file_patch 失败提示旧内容不匹配 → 重新读文件确认当前内容再patch</summary>
```

这里的"本次意图"就是本轮的目标。"上步结果"就是上轮目标是否达成的检查结果。

---

## 第二层：步骤级（Per-Step）—— Plan Mode 的核心执行单元

### 机制

在 `plan.md` 中，每个步骤都是一个明确的目标单元：

```markdown
## 执行计划
1. [ ] 步骤1简述
   SOP: xxx_sop.md
2. [ ] 步骤2简述
   SOP: yyy_sop.md
```

### 目标设定

写 plan.md 时，每个步骤必须包含：
- **动作描述**（做什么）
- **SOP 标注**（怎么做，有现成流程则引用）
- **依赖关系**（前置条件）
- **委托标记**（`[D]` 代表需 subagent 执行）

### Mini 验证（执行后立即检查）

执行完每个步骤后，强制进行 **Mini 验证**：

| 验证项 | 方法 |
|--------|------|
| 文件创建类 | `file_read` 确认文件存在且非空 |
| 数据操作类 | 检查 exit code / 输出行数 |
| 浏览器类 | `web_scan` 确认页面状态变化 |
| 代码修改类 | 重新读取确认改动生效 |

通过 → 标记 `[ ]` → `[✓ 简要结果]`
失败 → 记录失败，3次升级或标记 `[✗]`

### 依赖检查

执行一个步骤前，检查其依赖步骤是否都已标记 `[✓]`。这确保了目标的有序递进，不会跳步。

## 第三层：任务级（Per-Task）—— 完整任务的闭环验证

### 机制一：plan.md 终止检查

所有步骤标记完成后，**不可跳过**的终止检查：

```
file_read(plan.md) 全文扫描
→ 确认所有步骤（含[VERIFY]）均为 [✓] 或 [✗]
→ 0 个 [ ] 残留
→ 输出：🏁 终止检查：[总步数]步全部完成，0个[ ]残留 → 任务结束
```

### 机制二：验证态（独立 Subagent 验证）

这是最正式的"事后检查"机制。所有 plan mode 的任务完成后，**强制启动独立验证 subagent**：

```
┌─────────────────────────────────────┐
│  步骤8：准备验证上下文                 │
│  → 创建 verify_context.json          │
│     ├─ task_description（用户原话）    │
│     ├─ plan_file（plan.md路径）       │
│     ├─ task_type（code/data/browser） │
│     ├─ deliverables（交付物清单）      │
│     └─ required_checks（必做检查列表） │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│  步骤9：启动验证 subagent            │
│  → 对抗性验证                       │
│  → "证明交付物不能用"                │
│  → 输出 VERDICT                     │
└──────────────┬──────────────────────┘
               │
        ┌──────▼──────┐
        │  VERDICT    │
        ├─ PASS ✅    │
        ├─ FAIL ❌    │
        └─ PARTIAL ⚠ │
               │
        按结果处理/修复
```

### 机制三：checkpoint 进度追踪

`update_working_checkpoint` 在长任务中持续追踪目标进度：

```
[当前] 任务：XXX
[进度] 步骤2/5 完成
[目标] 下一步：步骤3 - 执行YYY
[约束] 关键限制条件...
```

任务中可随时回读 checkpoint，对比"当前状态"与"预定目标"是否偏离。

## 第四层：会话级（Per-Session）—— 跨任务的长期演进

### 机制：会话结束后蒸馏

长任务（15+ 轮）完成后触发 `start_long_term_update`，对整个会话进行回顾：

```
① 回顾会话全过程
   ├── 初始目标是什么？
   ├── 实际达成了什么？
   └── 偏差在哪里？

② 提取经验
   ├── 什么策略有效？
   ├── 什么坑踩了？
   └── 什么信息值得长期记住？

③ 按 META-SOP 决策树分类
   ├── 环境特异性事实 → L2 global_mem.txt
   ├── 通用操作规律   → L1 RULES
   └── 特定任务技术   → L3 SOP / utils

④ 写入对应层级
⑤ 同步更新 L1 Insight 索引
```

这确保了 **"这次踩的坑，下次不会再踩"**——跨会话的演进闭环。

## 第五层：自主行动模式（Autonomous Operation）

在用户不在线的自主行动中，目标设定与检查同样存在：

### 目标设定

通过 `set_todo()` 获取待办事项列表，每次选取一条执行：

```
- 有未完成条目 → 取一条，直接执行
- 无 TODO → 读 task_planning.md 规划新目标
- 不连续两次选相同子任务
```

### 事后检查

每次自主行动完成后的 **收尾 4 件事**（缺一不可）：

```
0️⃣ 重读 autonomous_operation_sop（格式化检查）
1️⃣ 写报告到 cwd（记录做了什么、结果如何）
2️⃣ complete_task() → 自动编号、归档、写入 history
3️⃣ set_todo() → 将已完成条目标记为 [x]
4️⃣ 结束，剩余留到下次
```

### 用户审查门

对于修改 global_mem、安装软件等不可逆操作，**必须写入报告待审**，用户归来后审查决定是否批准。这是最高级别的目标验证。

---

## 失败时的目标修正机制

当目标未达成时，系统不是简单重试，而是按 **3 次升级链** 逐级深入：

| 次数 | 行为 | 目标处理方式 |
|------|------|-------------|
| 1次失败 | 读错误日志，理解原因 | 调整执行策略，目标不变 |
| 2次失败 | 探测环境状态，获取更多上下文 | 审视目标是否合理，调整方法 |
| 3次失败 | 深度分析后换方案或问用户 | 可能需要修正目标本身 |

**关键原则**：**禁止无新信息的重复尝试**。每次重试必须基于新的信息或不同的策略。

## 各层级对比总表

| 层级 | 粒度 | 目标设定方式 | 检查方式 | 失败处理 |
|------|------|-------------|---------|---------|
| 单轮级 | 1 次回复 | `<summary>` 本次意图 | 下轮 `<summary>` 回顾结果 | 3次升级链 |
| 步骤级 | 1 个操作单元 | plan.md 的 `[ ]` 项 | Mini 验证（读/查/确认） | 3次升级或标记 `[✗]` |
| 任务级 | 完整任务 | plan.md + 自检清单 | 终止检查 + 验证 subagent | 修复后重验证 |
| 会话级 | 跨任务会话 | 无显式设定 | `start_long_term_update` 回顾 | 经验写入记忆 |
| 自主模式 | 单次自主行动 | `set_todo()` 选一条 | 收尾4件事 + 用户审查 | 写入报告待审 |

---

## 总结

本 Agent 的演进目标设定与检查机制是一个**层层递进、相互嵌套**的闭环系统：

1. **每轮有意图**（`<summary>`）—— 最小粒度的目标声明
2. **每步有验证**（Mini 验证）—— 执行后立即确认
3. **每任务有终检**（终止检查 + 独立验证 subagent）—— 对抗性验证确保质量
4. **每会话有蒸馏**（`start_long_term_update`）—— 跨会话经验沉淀
5. **自主有归档**（报告 + 历史 + 待办标记）—— 离线场景也不丢失闭环

这套机制的核心价值是：**每一个行动都有预设目标，每一个目标都有事后验证，每一次验证都推动系统演进。**
