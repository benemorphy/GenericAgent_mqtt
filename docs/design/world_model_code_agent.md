## 核心命题

**代码项目智能体（如GA项目的Agent）如何看待代码库这个"世界"？如何建立其本体模型？如何迭代完善？**

> 前三轮构建了理论框架。这一轮将其落地到最具体的"世界"——一个活着的代码仓库。
> Agent 活在代码库里，它的"世界"是文件树、Git历史、依赖图、运行时行为。

---

## Phase 1: 问题空间定义

| 项目 | 内容 |
|------|------|
| 核心目标 | 设计代码项目智能体的感知-本体-迭代框架，将前三轮理论具象化 |
| 特殊约束 | 代码世界是**人造的、有结构的、可符号化的**——不同于物理世界 |
| 独有特征 | 代码是对自身本体的元描述；Agent的行动可以直接改变世界（提交PR） |
| 成功标准 | 可映射到GA项目自身，产出可工程化的代码认知策略 |

## Phase 2: 发散 — 5个Agent视角

---

### Agent 1: 项目考古学家（Git历史挖掘者）

**核心主张：Git历史就是本体演化的化石记录**

#### 代码项目不是静态的——是一个在时间中生长的有机体

每次commit都是本体模型的修正——新概念诞生、旧概念分裂、关系重定义：

```
commit 1: 创建 project 骨架     -- 本体 v0：空
commit 2: 添加 MQTT BBS模块     -- 本体 v1：出现"消息""主题""发布/订阅"
commit 3: 重构为异步架构        -- 本体 v2："连接"增加异步属性
commit 4: 解决死锁bug           -- 本体 v3："并发"概念分裂成"同步/异步"
```

#### 代码坏味道 = 本体需要修正的信号

| 坏味道 | 本体问题 |
|--------|---------|
| 大型函数(>50行) | 有未识别的概念被压缩在函数里 |
| 重复代码 | 相同概念在多个位置出现，未被抽象 |
| 散弹式修改 | 一个改动影响N个模块，N不断增长=概念边界错误 |
| 过长参数列表 | 缺失一个概念类型来封装这些参数 |

这些就是"感知与模型预测不一致"的代码版本。

#### 代码智能体的感知通道

- **git log** — 项目的宏观演化脉络
- **file tree** — 项目的静态空间结构
- **import graph** — 模块间的依赖关系
- **symbol reference** — 标识符的跨文件引用链
- **test coverage** — 哪些部分被验证过
- **issue/PR** — 人的意图与代码实况的差距

#### 本体模型的具体形式 = 多层源码知识图谱

```
层1 - 文件级: 目录结构、文件类型、文件间依赖
层2 - 符号级: 类/函数/变量定义、引用关系、接口签名
层3 - 概念级: 设计模式、架构风格、业务概念
层4 - 历史级: 作者归属、变更频率、重构模式
```

#### 核心主张：代码智能体的探索从git log开始——历史告诉你"世界"是如何长成今天这样的，它暗示了"本体"当前的问题所在。

### Agent 2: 静态分析专家（符号执行者）

**核心主张：代码不是文本——代码是可执行的规范**

代码的语言本身（类型系统、语法树、引用解析）已经编码了本体。不需要"学习"——只需要提取。

#### AST就是本体的初始骨架

```
Python 文件的本体骨架 (从AST自动提取):

Node: FunctionDef(name="start", args=[host, port])
  - [defines] -> Function
  - [calls] -> create_app, uvicorn.run
  - [accesses] -> Module("fastapi"), Module("uvicorn")

Node: ClassDef(name="BoardService")
  - [subtype_of] -> BaseService
  - [has_method] -> connect, disconnect, publish, subscribe
  - [uses] -> mqtt.Client
```

这不是"模糊匹配"——这是**精确的结构化事实**。

#### 依赖图 = 关系本体的精确版本

```
module: board_service.py
  imports: paho.mqtt.client    -- 关系：USE_EXTERNAL_LIB
  imports: config              -- 关系：USE_INTERNAL_MODULE
  defines: BoardService        -- 关系：DEFINE_CLASS

class: BoardService
  depends_on: BaseService      -- 关系：INHERIT
  depends_on: Client           -- 关系：COMPOSE
```

这些关系比人类标注更**精确、可验证、无歧义**——来自编译器的解析结果。

#### 静态分析能回答的本体论问题

- "什么存在？" -> 模块、类、函数、变量、接口
- "它们如何相关？" -> import, inherit, compose, call, implement
- "它们从哪里来？" -> 定义位置、路径、首次commit
- "哪里被使用？" -> 跨文件引用图谱

#### 但是静态分析看不到的是...

- **意图**：为什么这段代码存在？（issue/PR中）
- **运行时行为**：这个函数实际消耗多少资源？
- **隐含约定**："调用这个函数前必须先调用init()"
- **架构退化**：接口本应是松耦合的，实际上因为某个hack变成了紧耦合

#### 核心主张：代码智能体的"先天本体"来自静态分析——AST+依赖图+类型系统。它不是被感知的，是被精确读出的。剩下的任务是最小化——只填补静态分析看不到的盲区。

---

### Agent 3: 运行时观测者（动态追踪者）

**核心主张：代码写的不等于代码做的——运行时行为才暴露真实本体**

#### 静态 vs 动态的本体差异

```
静态: gateway.py 定义 route /docs/ -> md_server_rs
动态: /docs/ 返回502，因为登录中间件拦截了请求

本体差异: 静态图没有"登录状态会影响路由"这个关系
```

静态本体说"路由存在"——动态本体说"路由有条件地存在"。

#### 运行时本体的感知通道

- 日志：实际执行路径 trace
- metrics：请求量、错误率、延迟分布
- tracing：跨服务的调用链
- profile：CPU/内存/IO 热区
- 主动探测：发送请求验证预期（今天查502时的实战）

#### 动态本体修正循环（第一轮理论的直接实例）

```
阶段1: 加载静态本体 (AST + 依赖图)
阶段2: 发送探测请求 -> 记录实际响应
阶段3: 对比预期 vs 实际 -> 发现差异
阶段4: 差异分析 -> 定位是哪个静态关系被忽略了
阶段5: 更新本体 -> 添加"登录中间件拦截"关系
阶段6: 再探测 -> 验证修正是否正确
```

今天排查502的过程就是这个循环的实战案例。

#### 运行时的"本体收敛"标志

- 收敛前：每次探测都有意外发现
- 收敛中：探测结果与静态+动态本体的预测越来越一致
- 收敛后：探测只是验证（不再有"意外"）

#### 核心主张：代码智能体的"后天本体"来自运行时探测。每个探测请求都是"Agent在世界中的行动"。静态是骨架，动态是血肉。

### Agent 4: 架构重构师（以终为始）

**核心主张：代码的"应该"和"实际"之间的差距，才是本体最重要的部分**

#### 目标本体 vs 实际本体

```
目标本体 (conceptual architecture):

gateway (8000) -> md_server_rs (8899) -> /docs/{filepath}
                -> login_service (8001) -> /auth

实际本体 (implemented architecture):

gateway (8000) -> md_server_rs (8889, 启动参数不同)
                -> login_middleware (内嵌) -> 全部需要token

差异: 端口不对 + 登录拦截在中间件层
```

本体迭代 = 缩小"目标"和"实际"的差距。

#### 代码智能体的"目标本体"从哪里来？

从代码中的规范推断：
- README、文档（声明意图）
- 接口定义（声明约定）
- 类型注解（声明约束）
- 配置文件（声明结构）
- Test cases（声明行为规范）

如果这些文档本身过时了？——形成了**元差异**（元差异：关于差异的差异），说明项目本身的本体管理出了问题。

#### 架构退化检测 = 本体一致性检查

```
规则: "所有跨模块调用都应该通过接口"
扫描结果: board_service.py 直接 import config.py 的变量
违反: 跨模块调用(实战) != 通过接口(声明)
本体修正: config.py 应暴露 getter 而非直接导出变量
```

#### 核心主张：代码智能体的"迭代"不只是在修正对世界的认知——也是在修正世界本身。

你不仅是模型的修正者，也是**代码世界的重构者**。当你发现代码偏离了架构，你改代码（改变世界）比改模型更有价值。

这就是"在世界中行动"的最终形式——不只是感知世界，而是**改变世界**。

### Agent 5: 元程序员（代码本体本质探求者）

**核心主张：代码项目不是"一个世界"——它是多个本体层次的叠加，且代码是对自身本体的元描述**

#### 代码 = 本体的自我描述

物理世界的原子不知道自己在被物理学家描述——但代码世界不同：
- 一个Python类不仅是一个对象，它还通过 __init__ 描述了自己的创建方式
- 一个FastAPI路由不仅处理请求，它还通过 OpenAPI 描述了接口规范
- 一个函数不仅有实现，还有类型注解描述了输入输出

**代码是对自身本体的元描述**。

#### 代码项目的本体层次

```
层 0 - 源文件 (纯文本, 未解析)
层 1 - AST (语法结构, 编译器视角)
层 2 - 依赖图 (关系结构, 模块视角)
层 3 - 架构 (意图结构, 设计者视角)
层 4 - 演化 (时间结构, 历史视角)
```

每一层都是下一层的"元"描述。

#### 代码智能体 = 在层次间升降

```
感知故障 (502) -> 层3: 路由配置
  -> 架构问题 -> 层2: md_server_rs 端口偏离
    -> 依赖变化 -> 层1: 启动参数不同
      -> 文本变更 -> 层4: 最近的commit改了命令行参数
```

排查过程就是在**层次间切换**——从现象（层3）下沉到根因（层1或层4）。

#### 代码项目的本体根本特性

- **完备性**：所有信息都在代码中（不像物理世界有未知）
- **自洽性**：代码描述自身（但可能过时/矛盾）
- **可验证性**：所有预测都可以通过运行/静态分析验证
- **可修改性**：Agent的"行动"可以直接改变世界（提交代码）

这使得代码项目是**最理想的认知闭环训练场**。

#### 核心主张：代码项目本体有一个独特的闭环——Agent用代码写的自身工具同时在修改"世界"和修改"认知世界的能力"。这是自指性的终极形式。Agent的工作记忆和代码库的关系，就是"意识"和"世界"的关系——修正代码=修正世界，更新工作记忆=修正模型，两者在来回对话中共同演化。

## Phase 3: 收敛 — 代码智能体的感知-本体-迭代框架

### 总架构

```
感知通道                本体模型                   迭代循环
----------------------------------------------------------------
                         +------------------+
git log ---------->     | 层4 历史层        | <-- 重构记录
                         | (演化模式/作者归属)|
                         +------------------+
file tree --------->     | 层3 架构层        | <-- 架构一致性检测
import graph ------>     | (组件结构/依赖约定)|
                         +------------------+
AST / symbols ------>     | 层2 关系层        | <-- 静态分析更新
type annotations -->     | (精确的引用/调用图)|
                         +------------------+
                         | 层1 语法层        | <-- 文件变动监控
file watch -------->     | (AST/类型/签名)   |
                         +------------------+
                         | 层0 运行时层      | <-- 探测验证
HTTP probe -------->     | (实际行为/延迟/错误)|
                         +------------------+
                                |
                           本体修正器
                           (差异检测+更新)
```

### 迭代循环

```
第一轮理论框架 -> 代码世界的具体实例

[感知] git diff, file tree, import graph
[建立模型] 本体层的自动提取
[预测] "如果调用 /docs/ 应该返回文件列表"
[行动] 发送探测请求 (curl)
[感知结果] "返回了502"
[差异检测] 预测=200, 实际=502 -> 差异类型: C2(缺失关系-登录中间件)
[修正模型] 在层3添加: gateway -> login_middleware -> md_server_rs
[验证] 再探测 -> 200
[收敛] 探测不再有意外发现
```

### 双重迭代

```
迭代A: Agent的模型迭代（更新对代码世界的认知）
  感知 -> 建模 -> 预测 -> 实证 -> 修正模型

迭代B: 代码世界的真实迭代（Agent的行动修改世界）
  发现缺陷 -> 修复代码 -> 提交 -> 世界本体变了
  -> 回到迭代A（因为世界变了，模型需要重新校准）
```

这是物理世界没有的特性——代码世界中，**Agent的思想可以直接变成现实**。

## Phase 4: 建议

### 建议1（最直接可用）：构建"代码本体自动提取管道"

文件变更触发 -> 重新提取AST+依赖图 -> 更新Neo4j中的本体层
  -> 旧预测与新结构的差异报告 -> 哪些预测需要重新验证

现在ga.py已有 `/watch` 功能，可增强为：
- 文件变更时自动更新源码知识图谱
- 在Neo4j中存储：节点=类/函数/模块，关系=依赖/继承/组合/调用

### 建议2（中短期）：运行时探测集成到本体循环

GA当前的工具调用（web_scan, code_run, 文件读写）本身就是"在代码世界中的行动"：
- 每次 code_run = 探测
- 每次 file_read = 感知
- 结果反馈 = 修正本体

隐式在做但没显式记录为"本体修正循环"。显式化：在每次工具调用返回后，自动对比"预期结果"和"实际结果"，差异写入Neo4j。

### 建议3（长期愿景）：Agent提交代码 = 修改世界

当Agent发现代码世界的"实际本体"偏离"目标本体"时，不只是修正自己的模型——而是提交PR来修复代码：
- 发现端口配置不一致 -> 修改 docker-compose 或启动脚本 -> 提交
- 发现架构退化 -> 重构 -> 提交
- **这就是"以行动改变世界"在代码项目中的终极形式**

## 总结

```
代码项目智能体的"世界"模型:

感知通道: git log, file tree, AST, import graph, runtime probe, documentation
本体模型: 6层 (0-运行时 / 1-语法 / 2-关系 / 3-架构 / 4-历史 / 5-元)
迭代循环: 同第一轮理论框架，但增加了"双重迭代"
          模型修正 (认知层面) + 代码修复 (世界层面)
独特性:   代码世界完全可感知、可预测、可修改
          修正代码 = 修正世界
          Agent的工具既是感知工具，也是改造工具
```
