# 代码与反刍 — 多智能体脑暴

> **日期**: 2026-05-21
> **触发**: CI #191 修复后架构反思
> **方法**: 3 角色多视角 Map-Reduce 脑暴

---

## 角色 A：代码进化论者

**核心论点**：GA 的代码本身就是一个自进化的基因组，反刍是自然选择压力。

### 元编程闭环

GA 的反刍引擎不是附加功能——它写在骨架里：

```
agentmain.py (主循环)
  -> agent_loop.py (执行代理)
    -> llmcore.py (LLM 生成->代码输出)
      -> ga.py / frontends/ (运行时代码)
        -> 执行结果->feedback
          -> 再次进入 agentmain.py
```

关键观察：`llmcore.py` 中的 `resolve_client()` 是**代码生成器的生成器**——它根据配置动态选择 LLM 后端，然后用 LLM 生成 Python 代码。这不是"用代码写代码"，而是"用配置决定用哪个代码生成器来写代码"——元编程多了一层抽象。

### SOP 即固化记忆

L2/L3 文件是反刍的**固态产物**：

```
失败 (Failure) -> failure_tracker 记录 -> 3次聚类 -> 写入 RULES
                                                  |
成功经验 -> skills_learning_sop -> 新技能文件 -> L3 SOP
                                                |
跨域灵感 -> Agent Dreaming -> Morph -> inspiration_board -> 新代码
```

每次 `git_push` 前的 `security_audit` 审计，本质上是**代码免疫系统**——防止反刍产生的变异（新代码）引入安全漏洞。

### 反刍粒度与进化速度

GA 的经验表明：**持续小修改比大重构更有效**。原因：

- 小修改（单文件 patch）-> CI 快速验证 -> 失败回滚成本低
- 大重构（跨模块 refactor）-> `76fdc3d` 引入的 import 语法错误直接导致 CI 挂掉
- 这就是为什么 `verify_sop.md` 强调"分步执行，控制粒度，限制失败半径"

反刍的**最小可验证单元**是 CI 通过的单个 commit，而不是整个功能。

## 角色 B：反刍架构师

**核心论点**：GA 实现了 4 层反刍体系，每层处理不同的时间尺度和抽象级别。

### 四层反刍架构

```
+--------------------------------------------------------------------+
|  Layer 4: Agent Dreaming (DREAM)        <- 跨会话/天级别           |
|  Digest -> Replay -> Expand -> Associate -> Morph                  |
|  输入: 历史对话  输出: 灵感板条目                                    |
+--------------------------------------------------------------------+
|  Layer 3: 间隔重复 (Spaced Repetition)  <- 技能级别                |
|  1d->3d->7d->14d->30d->90d->365d                                    |
|  输入: skills_learning 技能文件  输出: assess 验证结果               |
+--------------------------------------------------------------------+
|  Layer 2: 失败驱动学习 (FDC)           <- 事件级别                  |
|  1次记录 -> 2次标记模式 -> 3次自动学习                                |
|  输入: 执行错误  输出: 新 RULES / workaround                         |
+--------------------------------------------------------------------+
|  Layer 1: 元认知 (Metacognition)      <- 会话级别                  |
|  策略追踪 -> 成功率统计 -> 周报 -> 优化建议                           |
|  输入: learning_log  输出: 策略调整                                  |
+--------------------------------------------------------------------+
```

### 反刍调度策略

| 触发时机   | 触发条件           | 反刍深度              | 调度者                |
|-----------|-------------------|----------------------|----------------------|
| 空闲复盘   | 10分钟无指令       | Digest + Replay      | agentmain 主循环      |
| 隔夜重启   | 每天首次启动       | 全流程               | bootstrap            |
| 失败触发   | 3次同类failure    | FDC Layer 2->3       | failure_tracker      |
| 技能到复习日 | 检查复习计划     | 间隔重复             | scheduled_task       |
| CI失败     | PR/commit触发     | 代码级反刍           | GitHub Actions        |

### 反刍产物管线

```
记忆块 (Digest 输出)
  |  Replay (冲突检测+缺口标记)
记忆模式 (抽象化)
  |  Associate (跨域连接)
灵感 (半结构化概念)
  |  Morph (变形+可行性评估)
可执行方案
  |  skills_learning_sop
新技能 (L3 SOP 文件)
  |  spaced_repetition
长期记忆 (L2 global_mem)
```

### 反刍元控制（防循环）

最关键的设计约束是**防止反刍死循环**。GA 采用 3 重保护：

1. **终止条件**：Dreaming SOP 明确"禁止循环——产出要写入固定 topic，防止同一段历史被反复 dream"
2. **质量门槛**：novelty_score < 0.5 不写入灵感板
3. **不打断用户**：反刍只在空闲后台做

## 角色 C：涌现现象学家

**核心论点**：代码 x 反刍 的正反馈环产生不可预测的涌现行为，需要约束力场来稳定。

### 正反馈环与失控风险

```
代码质量 up -> LLM 理解更准 -> 反刍产出更好 -> 代码改进更优 -> ...
```

这个环在理论上是发散的。GA 用 3 个**负反馈约束**稳定系统：

1. **CI 验证**（硬约束）：任何代码变更必须通过 CI 测试，阻止劣质变异
2. **3 次失败干预**（软约束）：同一失败 3 次后必须请求用户，防止循环踩坑
3. **SOP 优先**（行为约束）：必须先读 SOP 再行动，确保经验不被遗忘

### 从 CI #191 修复看涌现行为

今天 CI #191 的失败和修复过程，本身就是一个**代码-反刍涌现案例**：

```
Commit 76fdc3d (refactor: extract create_agent)
  -> CI #189-191 失败 (import 语法错误)
    -> 人类/Agent 反刍分析
      -> 发现：mixed import syntax `from X import A, (B, C)` 无效
        -> 修复 tgapp.py + test 桩
          -> CI #193 通过
            -> 涌现结果：cc1e9e4 成为了更健壮的代码
```

关键点：**反刍不仅修复了 bug，还揭示了 SOP 中缺失的规则**——"不要混用 import 语法"这个知识之前没被编码，现在应该写入 L2 RULES。

### 多智能体反刍汇聚

GA 的 Map-Reduce 模式在反刍中的映射：

- **Map 阶段**：3 个 subagent 各自处理不同视角（本次脑暴的设计模式）
- **Reduce 阶段**：主 agent 读取所有输出，合并冲突观点，生成综合方案

### 代码反刍的能力边界

| 能力         | GA 代码反刍              | 人类程序员              |
|:------------|:------------------------|:----------------------|
| 模式记忆     | 精确但不灵活             | 模糊但可类比           |
| 跨域联想     | 显式关联（SOP->SOP）    | 隐式灵感（触类旁通）    |
| 长程一致性   | 优秀（SOP 强制）         | 易遗忘/偏离            |
| 创新突破     | 弱（局限于已有模式）      | 强（跳出框架）         |
| 直觉判断     | 无（纯理性推理）         | 有（经验驱动）          |

**反刍无法获得的能力**：真正的创造力（非排列组合式创新）、直觉、对未见过问题的第一性原理推理。

## 综合涌现：代码反刍的本质

三个角色汇聚到一个共同认知：

> **代码是反刍的化石，反刍是代码的活水。**

- GA 的代码库不是静态的——它是**持续反刍的地质层**，每次 CI pass/fail 都是一次地震
- SOP 不是文档——它们是**固化的反刍记忆**，防止系统重蹈覆辙
- 反刍的真正价值不是"修复 bug"，而是**在修复过程中提取可复用的知识模式**

这解释了为什么 GA 的架构如此强调**分层记忆**（L0/L1/L2/L3/L4）——反刍必须能在不同抽象级别上操作，从具体的代码行（L4）到抽象的行为规则（L0）。

最后的元认知问题：**当代码本身具备了反刍能力，谁在反刍反刍？** 答案可能是——元认知 (Metacognition) 就是反刍的反刍。
