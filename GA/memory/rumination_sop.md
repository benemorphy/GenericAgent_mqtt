# 代码反刍 SOP — Code Rumination Standard Operating Procedure

> 基于两次完整的 Git 反刍回合（11 模块、5 修复、2 退役、1 改名、4 测试、3 文献式确认）提炼

## 反刍 vs 其他活动的区别

| 活动 | 对象 | 目的 | 不动手 |
|:----|:----|:----|:------:|
| Code Review | 刚写的代码 | 找 bug | ❌ |
| 代码反刍 | 已存在一段时间的代码 | 理解演化、提取模式 | ✅ |
| 重构 | 有问题的代码 | 改结构 | ❌ |
| Git 考古 | 单个文件的提交历史 | 理解为什么这么写 | ✅ |
| **CodeGraph 快照** | 全索引的代码库 | **秒级获取依赖/调用/复杂度** | ✅ |

**反刍铁律**: 不修改代码也能发现问题。如果不动手就没发现，说明反刍方向错了。

## 触发条件

| 条件 | 优先级 | 说明 |
|:----|:------:|:-----|
| 连续 3 次以上修改同一文件 | 高 | 该文件需要理解为什么总改 |
| 被用户批评过的代码 | 高 | 最值得反刍 |
| 双版本并存（Python/Rust） | 高 | 迁移计划应尽早制定 |
| bug 修复后 | 中 | 根因分析后的模式提取 |
| 闲时随机选一个冷门文件 | 低 | 防止遗忘 |
| 刚写完的代码 | 禁用 | 太近没新信息，去 Code Review |

## 反刍流程

### Phase 1: GIT 档案（5 分钟）

```bash
# 1. 提交频率和历史
git log --oneline --format="%h %ai %s" -- {file}

# 2. 一次性获取所有 diff 统计（替代逐条迭代）
git log --oneline --format="%h" -- {file} | while read h; do
  git diff --shortstat ${h}^1..${h} -- {file}
done

# 3. bug/fix 模式
git log --all --grep="bug\|fix\|hotfix" --oneline -- {file}

# 4. 文件活跃度排名
git log --pretty=format: --name-only | sort | uniq -c | sort -rn | head -20
```

**产出**: 提交时间线 + 每次 diff 大小 + bug 频次 + 初始/当前行数占比

### Phase 2: 结构快照（3 分钟）

- 当前行数、文件大小
- 函数/类数量
- 模块依赖（import 分析）

**产出**: 当前结构图

### Phase 3: 模式识别（5 分钟）

识别以下常见模式：

| 模式 | 判断 | 健康度 |
|:----|:----|:------:|
| **文献式** | 初始后极少改动（初始占比 >90%） | ✅ 最佳实践 |
| **先功能后 SOP 再测试** | Phase 3 后才补测试 | ⚠ 需警惕 |
| **胖单体** | 单文件 47KB+ 不拆模块 | ❌ 应拆分 |
| **死代码反弹** | 清理后同量级新增 | ⚠ 正常 |
| **双版本** | Python/Rust 并存 | ❌ 技术债务 |
| **粘合层** | 只做编排，逻辑在外部 | ✅ 健康 |

### Phase 4: 产出（2 分钟）

每次反刍产出必须包含:

1. **3 个发现**（好/中/差各一）
2. **健康度评估**（✅/⚠/❌）
3. **建议行动**（可执行，P0/P1/P2 分级）
4. **"无需改动"也是有效产出** — 确认健康本身就是价值

产出类型对照表：

| 产出类型 | 条件 | 行动 |
|:---------|:----|:-----|
| **修复** | 确认 bug/技术债务 | 立即改 |
| **忽略** | 文献式、粘合层、死代码反弹 | 标记健康 |
| **重构** | 胖单体、双版本 | 写 TODO，下次加功能前做 |
| **退役** | 有 Rust 取代版 | 替换并删除 |

## 反刍退出机制

| 条件 | 行动 |
|:----|:-----|
| 3 轮没有新发现 | 停止，记"代码健康" |
| 15 分钟无产出 | 停止，换文件 |
| 发现需要大重构 | 暂停，写 issue/TODO |
| 发现 LLM 调用超预算 | 暂停，写入 TODO |

## 反刍不做什么

- ❌ 不修改代码（除非确认修复）
- ❌ 不 Code Review 刚写的代码
- ❌ 不对提交数 <5 的文件反刍（信息不够）
- ❌ 不对只做过路径改名的文件反刍（dashboard_mqtt: 4 次提交全改名 → 0 产出）

## 实践验证

```
本 SOP 产生的两次反刍回合:
  11 模块 → 5 修复 → 2 退役 → 1 改名 → 4 测试 → 3 文献式确认
  有效产出率: 9/11 = 82%
  0 产出文件: dashboard_mqtt.py (文献式)
              llmcore.py (文献式)
              chatapp_common.py (文献式)
```
